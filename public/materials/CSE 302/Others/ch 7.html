1. Database Design Phases, Schema, Data Model & ERD vs Relational Schema

Database Design Phases (Slide 2)

সহজ বাংলায় ব্যাখ্যা (Slides 2, 3, 4 & 5)

১. কেন ER Diagram থেকে Relational Schema-তে রূপান্তর (Conversion) প্রয়োজন? (Slide 2):
বাস্তব জীবনে একটি সফটওয়্যার বা ডাটাবেজ তৈরির শুরুতে ক্লায়েন্টের চাহিদা শুনে আমরা কাগজে-কলমে একটি নকশা আঁকি, যাকে Conceptual Design বা ER Diagram বলে। কিন্তু MySQL, Oracle বা PostgreSQL-এর মতো আসল ডাটাবেজ সফটওয়্যার সরাসরি ছবি (আয়তক্ষেত্র, ডিম্বাকৃতি, ডায়মন্ড) বুঝতে পারে না—তারা শুধু টেবিল (Tables / Relations) বোঝে! তাই ER Diagram-কে টেবিলের কাঠামো বা Relational Schema-তে রূপান্তর করা অপরিহার্য।

২. Database Schema vs Data Model (Slide 3):
• Database Schema: ডাটাবেজের সামগ্রিক নকশা বা কাঠামো (টেবিলের নাম, কলামের নাম, ডাটা টাইপ ইত্যাদি) বর্ণনা করে।
• Data Model: ডাটা, ডাটার মধ্যকার সম্পর্ক এবং শর্তাবলি বর্ণনা করার টুলস ও নিয়মের সমষ্টি। যেমন: ER Model (High-level conceptual data model) এবং Relational Model (Record-based logical data model)।

৩. ER Diagram vs Relational Schema-এর পার্থক্য ও Slide 5 উদাহরণ (Slides 4 & 5):
ER ডায়াগ্রামে থাকে Entity Set (আয়তক্ষেত্র), Relationship Set (ডায়মন্ড) ও Attributes (উপবৃত্ত), এবং এটি Mapping Cardinality (যেমন 1:1, 1:N, M:N) দেখায়। অপরদিকে Relational Schema-তে থাকে Relations (Tables), Tuples (Rows), Attributes (Columns), Primary Key (PK) এবং Foreign Key (FK)।

কেন dept_id (FK) student টেবিলে গেল? কারণ অনেক ছাত্র (Many side) একটি ডিপার্টমেন্টে (One side) ভর্তি হয়। Many-to-One সম্পর্কে One পাশের Primary Key-টি Many পাশের টেবিলে Foreign Key হিসেবে বসে।

Exam-Ready English Answer: ER Diagram vs Relational Schema (5 Marks)

Basis ER Diagram (Conceptual Model) Relational Schema (Logical Model)
Design PhaseCreated during the Conceptual-design phase.Created during the Logical-design phase.
Main ComponentsEntity Sets, Relationship Sets, and Attributes.Relations (Tables), Tuples (Rows), and Attributes (Columns).
Keys & LinksUses Primary Keys and Partial Keys; links via diamonds.Uses Primary Keys (PK) and Foreign Keys (FK) to link tables.
CardinalityExplicitly describes Mapping Cardinality (1:1, 1:N, M:N).Does not directly describe Mapping Cardinality.
Slides 6 & 7 Entity Conversion Rules

2. Converting Strong Entity Set (Slide 6) & Weak Entity Set (Slide 7)

A. Strong Entity Set (Slide 6)

Strong Entity কী? যে Entity-র নিজস্ব Primary Key আছে এবং সে অন্য কোনো Entity-র ওপর নির্ভরশীল নয়, তাকে Strong Entity বলে।
Conversion Rule: Strong Entity-র নামে একটি টেবিল বানাও, তার সব Simple Attribute গুলোকে কলাম বানাও এবং আন্ডারলাইন করা অ্যাট্রিবিউটগুলোকে Primary Key ঘোষণা করো।
Slide 6 Example (location): এখানে latitude এবং longitude একসাথে মিলে Composite Primary Key গঠন করেছে।

ER Entity: location (latitude, longitude, description, last_visited)

B. Weak Entity Set (Slide 7)

Weak Entity কী? যে Entity-র নিজস্ব সম্পূর্ণ Primary Key থাকে না (শুধু একটি আংশিক কী বা Discriminator / Partial Key থাকে যা ড্যাশ লাইন দিয়ে আন্ডারলাইন করা থাকে) এবং যে নিজের অস্তিত্বের জন্য Strong (Owner) Entity-র ওপর নির্ভরশীল, তাকে Weak Entity বলে (ডাবল আয়তক্ষেত্র দিয়ে আঁকা হয়)।
Conversion Rule: Weak Entity-র জন্য একটি টেবিল বানাও। এতে থাকবে:
১) Weak Entity-র নিজস্ব সব অ্যাট্রিবিউট (Partial key সহ), এবং
২) তার Owner (Strong) Entity গুলোর Primary Key (যা এখানে Foreign Key হিসেবে আসবে)।
৩) টেবিলের নতুন Primary Key হবে = Partial Key + Owner-এর Primary Key(s)!

3. Converting Special Attributes (Composite, Multivalued & Derived)

Slide 8

Composite Attribute

কী? যে অ্যাট্রিবিউটকে আরও ছোট ছোট অংশে ভাগ করা যায়, যেমন (address)-কে ভাগ করলে পাওয়া যায় street, city, state, zipcode।
নিয়ম: মূল টেবিলে প্যারেন্ট অ্যাট্রিবিউট address-এর নামে কোনো কলাম হবে না; বরং তার সাব-অ্যাট্রিবিউটগুলো (Component attributes) আলাদা আলাদা কলাম হিসেবে যুক্ত হবে।

Multivalued Attribute (Double Oval)

কী? একজন কাস্টমারের একাধিক ঠিকানা বা একাধিক ফোন নম্বর থাকতে পারে (Double oval দিয়ে আঁকা হয়)। একটি সেলে একাধিক মান রাখা Relational Model-এ (1NF) নিষিদ্ধ।
নিয়ম: এর জন্য সম্পূর্ণ আলাদা একটি নতুন টেবিল (cust_addr) বানাতে হবে! সেখানে মূল টেবিলের PK (cust_id) যাবে FK হিসেবে এবং সবগুলো কলাম মিলে হবে Composite PK।

কী? যে অ্যাট্রিবিউটের মান অন্য অ্যাট্রিবিউট থেকে হিসাব করে বের করা যায় (Dashed oval)। যেমন: জন্মতারিখ (dob) থেকে বয়স (age) হিসাব করা যায়।
নিয়ম: Derived Attribute-কে Relational Schema-তে অন্তর্ভুক্ত করা হয় না (Ignored / Omitted)! কারণ বয়স প্রতিদিন বদলায়, তাই ডাটাবেজে শুধু dob সংরক্ষণ করা হয়।

4. Converting Relationship Sets (1:1, 1:N, M:N, Recursive & Identifying)

A. One-to-One (1:1) Relationship Set (Slide 11)

FK in Either Table (Nullable)

নিয়ম: 1:1 সম্পর্কে কোনো নতুন টেবিল বানানোর দরকার নেই। যেকোনো একটি টেবিলের Primary Key অপর টেবিলে Foreign Key (FK) হিসেবে যোগ করলেই চলবে (সাধারণত যে পাশে Total participation বা কম NULL হওয়ার সম্ভাবনা থাকে সে পাশে রাখা ভালো)। Slide 11-এ loan-এর PK (loan_id) customer টেবিলে Nullable FK হিসেবে রাখা হয়েছে (কারণ সব কাস্টমারের লোন নাও থাকতে পারে)।

customer
cust_id
name, street_address, city
loan_id (FK, Nullable)
loan
loan_id
amount

B. One-to-Many (1:N / N:1) Relationship Set (Slide 12)

PK of "1" Side → FK in "Many" Side

নিয়ম (খুবই গুরুত্বপূর্ণ!): 1:N সম্পর্কেও আলাদা টেবিল বানানোর দরকার নেই। এখানে "One (1)" পাশের টেবিলের Primary Key-টি "Many (N)" পাশের টেবিলে Foreign Key হিসেবে যাবে।
কেন উল্টোটা হয় না? Slide 12-এ একটি লোনের অধীনে অনেক কাস্টমার থাকতে পারে (customer পাশে Crow's foot / Many, আর loan পাশে One)। তাই loan-এর PK (loan_no) গিয়ে বসেছে customer টেবিলে! উল্টোটা করলে একটি লোনের রো-তে একাধিক কাস্টমারের আইডি রাখতে হতো, যা অসম্ভব।

customer (Many Side)
cust_id
cust_name, cust_street, cust_city
loan_no (FK, Nullable)
loan (One Side)
loan_no
amount

C. Many-to-Many (M:N) Relationship Set (Slide 13)

Creates a NEW Junction Table!

নিয়ম: M:N সম্পর্কে (যেমন: একজন কাস্টমার অনেকগুলো লোন নিতে পারে, আবার একটি লোন যৌথভাবে একাধিক কাস্টমারের নামে থাকতে পারে) অবশ্যই সম্পর্কের নামে একটি নতুন টেবিল (borrower) তৈরি করতে হবে!
এই নতুন টেবিলে থাকবে: উভয় টেবিলের Primary Key (cust_id ও loan_id) যা একসাথে টেবিলটির Composite Primary Key এবং আলাদাভাবে Foreign Key হিসেবে কাজ করবে। এছাড়া সম্পর্কের নিজস্ব কোনো অ্যাট্রিবিউট থাকলে (যেমন access_date) সেটিও এই নতুন টেবিলে বসবে।

customer
cust_id
cust_name, cust_street, cust_city
borrower (New Table)
cust_id (FK)
loan_id (FK)
access_date

loan_id
amount

D. Recursive Relationship Set (Slide 14)

কী? যখন কোনো Entity নিজের সাথেই সম্পর্ক তৈরি করে। যেমন: একজন employee (worker) আরেকজন employee (manager)-এর অধীনে কাজ করে (works_for)।
নিয়ম: একই টেবিলের Primary Key (emp_id) ওই টেবিলেই একটি নতুন নামে (Role name ব্যবহার করে, যেমন works_for_emp_id) Self-referencing Foreign Key হিসেবে যুক্ত হয়।

employee
emp_id
name
works_for_emp_id (FK → employee.emp_id)

E. Identifying Relationship Set (Slide 17)

কী? যে ডাবল-ডায়মন্ড সম্পর্ক (loan-payment) একটি Weak Entity (payment)-কে তার Owner Strong Entity (loan)-এর সাথে যুক্ত করে।
নিয়ম: Identifying Relationship-এর জন্য আলাদা কোনো টেবিল বানাতে হয় না! Owner-এর PK (loan_no) সরাসরি Weak Entity টেবিল (payment)-এ গিয়ে Partial Key (payment_no)-এর সাথে মিলে Composite PK গঠন করে।

loan_no
amount
payment
payment_no
loan_no (FK)
payment_date
payment_amount

Solved Exercise 3 (Slide 18): Sports Tournament ERD → Relational Schema

Slide 18 Complete Solution

ER ডায়াগ্রাম বিশ্লেষণ (Slide 18):
• PLAYER (PK: Pid): Basic_inf Multivalued হওয়ায় আলাদা টেবিল PLAYER_BASIC_INF হবে। IN (N:1) সম্পর্কের কারণে Tid (FK) PLAYER টেবিলে যাবে।
• OPPOSE (M:N Recursive on PLAYER): একজন প্লেয়ার অনেক প্লেয়ারের বিপক্ষে খেলে, তাই আলাদা টেবিল OPPOSE(Pid1, Pid2) হবে।
• TEAM (PK: Tid): Pid (Captain/Player ref) আছে, এবং T_inf Multivalued হওয়ায় আলাদা টেবিল TEAM_INF হবে।

6. Quick Revision Cheat-Sheet, Practice Problems & Exam Answers

ER Model Component Relational Schema Conversion Rule Key Assignment (PK / FK)
Strong Entity Set Create a separate table with all simple attributes. Entity's key becomes PK.
Weak Entity Set Create a table with its attributes + Owner's PK. PK = Partial Key + Owner's PK (also FK).
Composite Attribute Include only simple component attributes as columns. Parent composite name is omitted.
Multivalued Attribute Create a new separate table for the attribute. Composite PK = Entity PK (FK) + Attribute.
Derived Attribute Do not include in any relational table. Computed dynamically when queried.
1:1 Relationship No new table; add PK of one side into the other side. Added key acts as FK (often Nullable).
1:N Relationship No new table; add PK of "1" side to "N" side. Added key acts as FK in the "N" table.
M:N Relationship Create a new relationship table + its attributes. Composite PK = Both entity PKs (each is FK).
Recursive Relationship Add a renamed copy of the entity's PK to the same table (for 1:N) or new table (for M:N). Renamed column acts as self-referencing FK.

Exam-Ready English Answer: Rules for Converting ER Diagram to Relational Schema (8 Marks)

Converting a conceptual ER Diagram into a logical Relational Schema follows seven standard rules:
1. Strong Entity Set: Create a relation (table) containing all simple attributes of the entity, designating its primary key as the table's Primary Key (PK).
2. Weak Entity Set: Create a relation containing all attributes of the weak entity plus the Primary Key of its identifying owner entity as a Foreign Key (FK). The PK is the combination of the owner's PK and the weak entity's partial key.
3. Composite Attributes: Flatten composite attributes by including only their simple sub-attributes as columns in the relation.
4. Multivalued Attributes: Create a separate new relation containing the multivalued attribute and the PK of the owner entity (as FK); together they form a composite PK.
5. Derived Attributes: Omit derived attributes from the schema since their values can be computed dynamically.
6. Binary Relationships (1:1, 1:N, M:N): For 1:1, place the PK of one entity as an FK in the other. For 1:N, place the PK of the "1" side as an FK in the "N" side table. For M:N, create a new junction table containing the PKs of both participating entities (forming a composite PK) along with any descriptive attributes of the relationship.
7. Recursive Relationships: Include a renamed copy of the entity's PK within the same relation as a self-referencing Foreign Key (for 1:1 or 1:N) or create a separate relation (for M:N).
